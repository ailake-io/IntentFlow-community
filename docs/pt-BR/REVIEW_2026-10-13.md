# Revisão do projeto — 13/10/2026

## Escopo e resultado

Revisão do código Python, API/UI, autenticação, armazém, checks, linhagem, propostas de correção, diff de dados,
entrada OpenLineage, empacotamento, testes e documentação do escopo atual: camada de controle junto a dbt/orquestradores/warehouses.
O histórico do antigo motor próprio não foi usado como especificação vigente.

As correções abaixo estão aplicadas no workspace. Não foram acionados provedores externos de IA, serviços pagos ou notificações reais.
Dados de regressão e benchmarks são sintéticos/temporários; o armazém de trabalho não foi migrado nem editado.
Esta revisão não é certificação de segurança nem comprovação de todos os conectores em produção.

## Correções aplicadas

| Área | Problema encontrado | Correção |
|---|---|---|
| API: configuração | Endpoint genérico expunha valores de segredos e permitia alterar configurações internas/globais | Filtragem de chaves reservadas na leitura e rejeição na escrita; endpoint de usuários exige admin global |
| API: entrada | JSON não objeto, framing inválido e corpos grandes podiam gerar erros ou reter recursos | Limite de 1 MiB, timeout de leitura, rejeição de Content-Length inválido/duplicado, Transfer-Encoding e JSON inadequado |
| Conexões | Conexões do armazém sobreviviam a requisições e tarefas | Fechamento por requisição e em tarefas; Store admite context manager; conexão de diff fechada no finally |
| MFA | Reconfiguração podia apagar MFA ativo; uso concorrente podia reutilizar código | Reinicialização ativa recusada; consumo atômico de TOTP e recuperação; usuário sem MFA não passa em mfa_check |
| Segredos | Ausência de biblioteca/chave podia persistir novos segredos em texto claro | Novas gravações em armazéns persistentes falham sem cifragem; leitura legada e armazenamento transitório em memória preservados |
| SSO | Ausência de email_verified era aceita | Login exige email_verified explicitamente verdadeiro |
| IA: tarefas | Estado indexado só por achado misturava projetos e crescia sem limite | Chave por armazém/achado, lock, limite de 4 tarefas ativas, 128 registros e expiração de concluídas na criação de tarefas |
| Propostas: caminhos | Manifesto podia apontar para arquivo fora da raiz, inclusive via symlink | Resolução e contenção na raiz para regras e contexto enviado ao LLM |
| Propostas: política | Validação não estava vinculada à versão exata; exigência de build/revisão extra podia ser contornada | Hash da validação conferido na aplicação; build obrigatório quando indicado; revisão extra exige pessoa distinta do autor |
| Propostas: rollback | Reversão podia sobrescrever edição posterior | Confere todos os arquivos antes de restaurar; alterações posteriores fazem a reversão ser recusada |
| Checks e qualidade | Checks desabilitados, de outro estágio ou com erro podiam encerrar incidentes existentes | Só IDs de checks concluídos na rodada autorizam resolução; correspondência exata, sem prefixo |
| OpenLineage | START e COMPLETE em requisições distintas perdiam tempo inicial/duração; START atrasado reabria execução | Reutilização do estado persistido, identificação por job/run, preservação de estado terminal e cálculo de duração |
| Diff de dados | Nome de relação interpolado aceitava SQL; alteração só de tipo podia aparecer como igualdade | Parser restringe relações a identificadores, respeita normalização por dialeto; limites de amostragem e tipo entram na comparação |
| Linhagem | Travessia repetia nós/ciclos; cache podia misturar raízes; fork herdava threads nativas | Conjuntos de visitados, cache limitado e separado por raiz; processos spawn com contexto inicializado uma vez por worker |
| Armazém/performance | N+1 na contagem de notas; leitura integral de auditoria para overview; busca linear de token | Uma consulta agregada, últimas 30 entradas e consulta por hash com índices |
| Checks SQL/performance | Mesmo SQL era analisado novamente em 11 checks | AST compartilhado por modelo/dialeto/SQL dentro de cada execução |
| CLI/Python | F-string exigia Python 3.12 apesar do requisito mínimo 3.11 | Extraída expressão de redação de senha para variável; análise estática compatível com 3.11 |
| Docker e arquivos | Imagem executava como root; contexto/versionamento podiam incluir estado local | UID/GID 10001, extra de cifragem, .dockerignore e exclusões de bancos/chaves/.env/caches |
| Documentação | Negava existência de LLM e prometia isolamento/privacidade não garantidos | README, decisões, arquitetura, IA e implantação alinhados ao comportamento atual |

Principais arquivos: [web.py](../../src/intentflow/web.py), [store.py](../../src/intentflow/store.py),
`proposals.py` (hoje no IntentFlow Enterprise), [lineage.py](../../src/intentflow/lineage.py),

## Verificação

- Suíte completa após as correções de segurança e concorrência: **298 aprovados, 50 pulados**, em 159,66 s; nenhum aviso de fork.
- Foram acrescentados **47 casos de regressão** (incluindo parametrizações) em `tests/test_review_regressions.py`.
- Ruff: `E9,F63,F7,F82` aprovado em todo `src`, nas novas regressões e no script de benchmark. A análise identificou e permitiu corrigir uma f-string incompatível com o Python 3.11 declarado no projeto.
- A pequena alteração final da CLI foi conferida separadamente para preservar a ocultação de senha. O runtime usado foi Python 3.13.5; Python 3.11 não foi exercitado.
- Os 50 testes pulados não contam como verificados; incluem integrações/dependências opcionais.

O teste de linhagem compara execução serial e paralela com DuckDB ativo. As regressões adicionais exercitam permissões,
framing HTTP, consumo concorrente de MFA, estados OpenLineage, contenção de caminhos, políticas e hashes das propostas,
normalização de identificadores SQL, consultas agregadas e cifragem indisponível.

A suíte foi executada sem variáveis INTENTFLOW_* herdadas, com telemetria dbt desabilitada; serviços opcionais mantiveram seus skips.
Não foram construídas imagens Docker nem efetuada auditoria de CVEs das dependências. Verificações de código não equivalem a teste
real de todos os drivers, provedores OIDC ou serviços cloud.

## Limites registrados na revisão e próximas melhorias

| Prioridade | Limite comprovado no código | Próxima melhoria |
|---|---|---|
| Alta | Validação dbt usa cópia temporária, mas herda acesso do processo; macros/hooks/build podem escrever no destino do perfil | Executar em processo/contêiner dedicado, com ambiente mínimo, limites e perfil exclusivo de teste antes de aceitar projetos não confiáveis |
| Alta | Aplicação/rollback de múltiplos arquivos não é transação; falha entre gravações ou edições concorrentes pode deixar estado parcial | Backup durável anterior à escrita, lock do projeto e protocolo de recuperação com estado intermediário |
| Alta | Filtragem de evidências enviadas à IA remove apenas campos superiores; SQL/texto/aninhamentos podem conter dados | Para a demonstração de gasto zero, manter provedor externo desligado; acrescentar visualização exata do payload e política de redação antes de uso externo |
| Média | Segredos legados em texto claro continuam legíveis; mudar a chave não recifra valores existentes | Conferir secrets status, migrar dados legados e planejar rotação com backup protegido |
| Média | Servidor HTTP e coordenação de tarefas são locais; limites de IA e locks não abrangem vários processos | Antes de escala, fila/leases compartilhadas, proxy com limites de conexão e rate limiting de autenticação |
| Média | Eventos OpenLineage e execução de checks não têm coordenação transacional entre múltiplas instâncias | Transações/versões por execução e lease de agendamento; testar eventos simultâneos e reentrega |
| Média | Diff com chaves duplicadas pode multiplicar pares no JOIN; igualdade com chaves nulas/duplicadas precisa de contrato explícito | Validar unicidade/nulidade ou definir estratégia multiconjunto antes de comparações grandes |
| Média | Auditoria de CVEs não roda automaticamente e não abrange a imagem-base do sistema operacional | Automatizar auditoria/atualização em CI e incluir varredura da imagem/base OS |
| Média | Resolução de achados conhece execução bem-sucedida do check, não cobertura de cada fonte | Registrar indisponibilidade por fonte e evitar interpretar coleta vazia/incompleta como ausência de problemas |

Essas pendências não foram tratadas como garantias já entregues. Qualidade e linhagem continuam sendo requisitos desde a ingestão
até o consumo; os caminhos exercitados aqui não provam cobertura de todos os sistemas externos.

## Compatibilidade e operação

- MFA já ativo exige o fluxo de desativação/reset autorizado antes de cadastrar outro segredo.
- SSO sem email_verified=true será recusado; ajustar o mapeamento no provedor de teste.
- Propostas antigas sem hash de validação precisam ser validadas novamente; revisão extra exige outra pessoa.
- Sem cryptography/chave, novos segredos persistentes são recusados. Instalar o extra secrets e configurar chave para PostgreSQL.
- Volumes Docker existentes precisam permitir acesso ao UID/GID 10001; não usar permissão global de escrita.
- spawn pode ter custo inicial maior que fork; o servidor continua usando cálculo serial com cache.
- Backups dos arquivos originais desta revisão: /tmp/intentflow-review-20261013. Não são backup durável dos dados do projeto.

## Preparação de produção — 13/10/2026

- `uv.lock` foi gerado para as dependências de todos os extras; o Dockerfile passou a instalar os extras `secrets` e `postgres` com `uv sync --locked`.
- As imagens-base Python e uv estão fixadas por digest. A imagem `intentflow:lock-check` foi construída (sha256:b87ac24cf24730e9298dcbc58aa41c197ff58047df227cd0839282aed85ed17f); `intentflow --help` iniciou em container descartável, sem rede e com filesystem read-only. A imagem não recebeu uma varredura CVE do sistema operacional nem teste de inicialização do servidor.
- Criação de correções determinísticas e leitura de arquivos no contexto enviado à IA agora compartilham o lock do projeto com apply, rollback e staging dbt. Isso coordena operações do IntentFlow, mas leitores externos ainda podem observar parte do lote durante os renames; visibilidade atômica universal continua exigindo leitor cooperativo ou layout versionado.
- A auditoria de `uv.lock` encontrou `oauthlib 3.3.1` vulnerável no extra Databricks (`PYSEC-2026-4114`). O conector Databricks 4.6.0 restringe `oauthlib <4.0.0`; a versão corrigida indicada é 4.0.0. O extra Databricks não entra na imagem padrão e deve ficar desabilitado até atualização compatível do conector.
- A auditoria do conjunto instalado na imagem padrão (`secrets` e `postgres`) não encontrou CVEs conhecidas; não cobre as imagens-base do sistema operacional nem substitui varredura contínua.
- Suíte ampla após as mudanças: **318 aprovados, 52 pulados**, em 271,59 s; um aviso do Snowflake connector sobre urllib3/chardet. A carga isolada passou: p50 1,257 s, p95 1,806 s, máximo 1,987 s. O container padrão passou a auditoria Python sem CVEs conhecidas; a auditoria de todos os extras ainda encontra o problema Databricks acima.

## Decisões do usuário

Nenhuma decisão é necessária para conservar as correções aplicadas. Permanecem válidos Linux, recursos locais, dados sintéticos e gasto zero.
Para etapas futuras, basta indicar uma prioridade, por exemplo:

- **"Prioridade: isolar validação em contêiner local"** — segurança ao executar dbt.
- **"Prioridade: aplicação atômica e recuperação"** — proteção contra falhas durante correções.
- **"Prioridade: benchmark local maior; limite de RAM X GB"** — medição além da demonstração pequena.

Não é necessário fornecer contas, credenciais ou dados externos para essas etapas.
